# ExcelMcp improvement-feasibility constraints — 2026-08-05

## Scope

This is a constraint note, not an implementation plan. It uses Microsoft/.NET documentation, the MCP specification, and the checked-out ExcelMcp source at `60d25c08caefd3726b8e24419b1569ed99e41731`; no secondary sources were used. “Unknown” means the consulted owner documentation supplies no guarantee, not that the idea cannot work.

## Findings

| Idea | Source-backed feasibility boundary | Assessment |
| --- | --- | --- |
| 1. COM/STA cancellation | ExcelMcp already puts an `ExcelBatch` on one STA and serializes its work through a channel. [.NET cancellation is cooperative](https://learn.microsoft.com/en-us/dotnet/standard/threading/cancellation-in-managed-threads): a cancellation request cannot preempt a COM call that does not observe it. The MCP cancellation notification is also only a request; a receiver may be unable to cancel it. [MCP cancellation](https://modelcontextprotocol.io/specification/2024-11-05/basic/utilities/cancellation) | **Constrained.** Distinguish “stop waiting” from “operation stopped.” After a deadline, quarantine/close the session and report an indeterminate mutation state; do not promise rollback or exactly-once execution. |
| 2. Excel-process isolation | Microsoft describes Office as non-reentrant and STA-based with global resources; multiple instances can race. For more than one instance, it says to isolate at the VM level. [Microsoft guidance](https://learn.microsoft.com/en-us/office/client-developer/integration/considerations-unattended-automation-office-microsoft-365-for-unattended-rpa) | **Only a resilience boundary.** A child process makes forced termination possible, but it cannot make in-process Excel calls safely cancellable or make multi-tenant pooling safe. |
| 3. Bounded channels / backpressure | A bounded `Channel` has a maximum capacity; its default `Wait` mode blocks `WriteAsync` until room is available. Drop modes discard work. [.NET Channels](https://learn.microsoft.com/en-us/dotnet/core/extensions/channels) | **Feasible.** Replace the current unbounded STA queue only with a wait/reject policy for mutations; dropping a workbook write is not a valid overload policy. Size and admission limits need measurement. |
| 4. Targeted semantic inspection and caching under manual/VBA edits | `Worksheet.Change` covers user or external-link cell changes but explicitly does not fire for recalculation; `Calculate` is a separate event path. [Worksheet.Change](https://learn.microsoft.com/en-us/office/vba/api/excel.worksheet.change) [Calculate](https://learn.microsoft.com/en-us/office/vba/api/excel.application.calculate) Excel’s coauthoring guidance likewise warns that cached add-in values become stale and Excel syncs workbook content, not add-in memory. [Coauthoring](https://learn.microsoft.com/en-ie/office/dev/add-ins/excel/co-authoring-in-excel-add-ins) | **Feasible as an advisory cache, not a correctness cache.** Invalidate on observed events and after own mutations; re-inspect/fingerprint before a dependent write. Arbitrary VBA/add-in/object-model changes remain an unknown invalidation surface. |
| 5. Server-side batching / vectorized COM writes | Assigning a two-dimensional array to `Range.Value` writes a multi-cell range in one operation; Microsoft notes that multi-area ranges are not properly supported. [Range.Value](https://learn.microsoft.com/en-us/office/vba/api/excel.range.value) | **Strong near-term candidate** for contiguous rectangular value/formula writes. Preserve operation order and use an explicit fallback for disjoint ranges, formats, tables, and side-effecting actions. |
| 6. Screen updating, calculation, and event suppression | `ScreenUpdating=False` can speed macros and must be restored. `EnableEvents=False` suppresses events such as `BeforeSave`; calculation mode is application-level and OLAP sources only allow `xlNormal`. [ScreenUpdating](https://learn.microsoft.com/en-us/office/vba/api/excel.application.screenupdating) [EnableEvents](https://learn.microsoft.com/en-us/office/vba/api/excel.application.enableevents) [Calculation](https://learn.microsoft.com/en-us/office/vba/api/excel.application.calculation) | **Feasible, but scoped.** Snapshot/restore every setting in `finally`; do not suppress calculation/events around refresh, VBA, or workflows whose event semantics matter. |
| 7. Idempotency | MCP defines tool invocation and cancellation, but no exactly-once or idempotency-key semantics. [Tools](https://modelcontextprotocol.io/specification/2024-11-05/server/tools) [Lifecycle](https://modelcontextprotocol.io/specification/2025-06-18/basic/lifecycle) | **Protocol does not supply this.** A server-side operation ID plus durable receipt can deduplicate a retry only when the prior outcome is known. Excel mutations need command-specific preconditions/verification; a timeout after COM dispatch is intrinsically “unknown,” not safely replayable. |
| 8. Durable flush, atomic replace, and checkpoint safety | `FileStream.Flush(true)` flushes intermediate file buffers; `File.Replace` replaces a destination and can create a backup, but source/destination must share a volume. [Flush](https://learn.microsoft.com/en-us/dotnet/api/system.io.filestream.flush) [Replace](https://learn.microsoft.com/en-us/dotnet/api/system.io.file.replace) | **Feasible improvement, not a power-loss proof.** Flush the completed checkpoint before publishing it; use same-volume replacement plus a retained backup and hash/size validation. The APIs do not establish a whole-workflow transaction with Excel’s own save path. |
| 9. PID reuse / start-time validation | Windows can reuse a process ID after its process exits. `Process.StartTime` identifies the associated local process’s start time and throws when it has exited. [Process.Id](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.process.id) [Process.StartTime](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.process.starttime) | **Feasible hardening.** Store PID + start time (and verify `EXCEL` identity) before any kill/health action. PID alone is unsafe; start-time reads can themselves fail during exit. |
| 10. Performance and chaos testing | The project intentionally relies on real-Excel integration testing because COM behavior is environment-dependent. [Test rationale](https://github.com/sbroenne/mcp-server-excel/blob/60d25c08caefd3726b8e24419b1569ed99e41731/tests/README.md#L1-L75) Microsoft’s unattended guidance calls for thorough testing plus monitoring/restart mechanisms. [Microsoft guidance](https://learn.microsoft.com/en-us/office/client-developer/integration/considerations-unattended-automation-office-microsoft-365-for-unattended-rpa) | **Necessary validation work; no official throughput/SLO target exists.** Define an owned benchmark corpus and fault matrix (hang, crash, lock, prompt, partial save), then publish measured limits by Excel/version/bitness. |
| 11. Compact/dynamic MCP tool surface | `tools/list` is paginated. A server can advertise `listChanged` and should notify clients when the tool list changes. [MCP tools](https://modelcontextprotocol.io/specification/2024-11-05/server/tools) | **Feasible compatibility feature.** A smaller capability- or session-specific surface must keep stable names/schemas for existing clients and send list-change notifications where supported; client refresh behavior is not guaranteed by the protocol. |
| 12. Warm Excel process pooling | Microsoft says Office applications use global resources, are non-reentrant, and can become unstable in unattended use; it recommends monitoring and restart. [Microsoft guidance](https://learn.microsoft.com/en-us/office/client-developer/integration/considerations-unattended-automation-office-microsoft-365-for-unattended-rpa) | **High-risk / unproven.** A warm, single-owner interactive session is different from a reusable worker pool. There is no Microsoft guarantee for safe cross-workbook, cross-user, or long-lived pooling; use bounded soak tests before expanding session lifetime. |
| 13. Operation reordering / query optimizer | Excel calculation may be workbook-, worksheet-, or range-scoped, so observably equivalent ordering is context-dependent. [Application.Calculate](https://learn.microsoft.com/en-us/office/vba/api/excel.application.calculate) Office automation is non-reentrant and shares global resources. [Microsoft guidance](https://learn.microsoft.com/en-us/office/client-developer/integration/considerations-unattended-automation-office-microsoft-365-for-unattended-rpa) | **Only safe for a deliberately restricted algebra.** Reorder only operations declared independent and non-observable; treat formulas, events, calculation, VBA, refresh, names, tables, and UI state as ordering barriers. No general equivalence guarantee was found. |
| 14. Distributed Excel workers / unattended automation / licensing | Microsoft does not recommend or support noninteractive server-side Office automation because it may be unstable or deadlock. Its unattended-RPA option is Windows-only, requires a qualifying license, and permits one physical or virtual OSE per license; without it Excel is reduced-functionality and cannot create/edit/save. [Automation guidance](https://learn.microsoft.com/en-us/office/client-developer/integration/considerations-unattended-automation-office-microsoft-365-for-unattended-rpa) [Licensing](https://learn.microsoft.com/en-us/microsoft-365-apps/licensing-activation/overview-unattended) | **Do not position as a supported general server platform.** If pursued under the RPA terms, design per-VM isolation, licensing/identity boundaries, prompt/macro handling, health monitoring, and restart/recovery as mandatory operating controls. |
| 15. Shadow formula engine | Open XML stores formula text plus cached values, and a reader may calculate later. The Open XML SDK explicitly provides no Excel recalculation, data refresh, or application behavior. [Formulas](https://learn.microsoft.com/en-us/office/open-xml/spreadsheet/working-with-formulas) [SDK limits](https://learn.microsoft.com/en-us/office/open-xml/open-xml-sdk-design-considerations) | **Feasible only as a partial validator/estimator.** It cannot be represented as Excel-parity without an owned compatibility matrix for functions, dynamic arrays, external links, names, add-ins/UDFs, VBA, data model, and locale/version behavior. |
| 16. Workbook branching / merging | Excel coauthoring warns of stale cached state, lost changes, and merge conflicts; structural table-row edits can conflict. [Coauthoring](https://learn.microsoft.com/en-ie/office/dev/add-ins/excel/co-authoring-in-excel-add-ins) Office sync conflict resolution does not offer `msoSyncConflictMerge` for Excel workbooks. [Sync.ResolveConflict](https://learn.microsoft.com/en-us/office/vba/api/office.sync.resolveconflict) | **A generic semantic merge is unsupported.** A product can offer copy-based branches and explicit, domain-specific range merges with conflict review, but must not imply Git-like workbook merging for formulas, tables, charts, VBA, connections, or concurrent structural edits. |

## Decision-relevant unknowns

- No first-party source located promises safe warm pooling, arbitrary operation reordering, formula-engine parity, generic workbook merge, or a universal performance/chaos threshold.
- The evidence supports bounded admission, rectangular COM writes, scoped state restoration, process-identity checks, and checkpoint durability as incremental engineering work. It does **not** remove the Excel/Office automation constraints above.
- Any retry/recovery design must retain an explicit `unknown` terminal outcome for a process loss or timeout after a potential COM mutation.
